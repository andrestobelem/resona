Estudio de Remotion para Resona

> Estado: investigación técnica sobre Remotion `v4.0.506`, commit > `5e5586f9e9dc5624a74cfe2a4e9c969957a6f3ec`, realizada el 2026-08-04.

Conclusión ejecutiva

Sí: Remotion es una referencia mucho más rica que “usar componentes para producir un archivo”. Su arquitectura une una fuente programable con cinco superficies coherentes: registro de composiciones, Studio, Player embebible, renderer programático y CLI. El código del autor se compila una vez, las variantes se resuelven mediante inputs y metadata, y las superficies interpretan el mismo contrato en lugar de mantener modelos paralelos ([README][readme-source-of-truth], [bundle][docs-bundle], [Player][docs-player-integration]).

La idea principal que Resona debería adoptar es esa continuidad:


fuente versionable
        ↓
composición + inputs + metadata
        ↓
modelo normalizado compartido
   ┌────┴────────┐
   ↓             ↓
Studio/Player    renderer offline

La implementación central de Remotion, en cambio, no se puede trasladar literalmente. Remotion puede evaluar y renderizar cuadros independientes en paralelo; audio, MIDI, instrumentos y efectos forman un sistema continuo y con estado. El equivalente correcto no es `frame -> muestra`, sino: 


programa de composición
        ↓
eventos + grafo + automatizaciones
        ↓
motor stateful que procesa bloques de muestras

El propio pipeline de audio de Remotion confirma la diferencia: durante el render registra por cuadro referencias a assets, posición y volumen; después reconstruye intervalos y curvas, preprocesa los archivos y los mezcla. No es un motor DAW ni un grafo DSP ejecutado de forma continua ([AudioForRendering][src-audio-rendering], [calculateAssetPositions][src-asset-positions], [createAudio][src-create-audio]).

La recomendación es copiar la forma de producto y sus límites entre módulos; adaptar tiempo, reproducción, render y edición visual; y no copiar ni el renderer basado en Chromium/FFmpeg ni la escala actual del monorepo.

Advertencia sobre “copiar”

En este documento, **copiar** significa adoptar una idea, un contrato o un patrón propio, no copiar código fuente. La licencia del snapshot permite ciertos usos de Remotion, pero prohíbe copiar o modificar su código para vender, licenciar o sublicenciar un derivado ([licencia][license-restriction]). Cualquier reutilización literal necesita una revisión jurídica independiente; este informe no es asesoramiento legal.

Alcance y método

Se estudió un clon local shallow, limpio y fijado al tag `v4.0.506` y al commit completo indicado arriba. Por ser shallow, este informe no usa conteos de commits, antigüedad, contribuidores ni evolución histórica como evidencia. Las conclusiones se basan en:

- documentación oficial incluida en el monorepo y publicada en `remotion.dev`; - implementación actual de core, bundler, renderer, CLI, Player, Studio y protocolo; - pruebas unitarias, de integración y contratos del monorepo; - manifests y configuración de build del mismo snapshot.

Cada afirmación sobre el funcionamiento actual lleva una fuente primaria. Las hipótesis sobre por qué el producto tuvo éxito están separadas y rotuladas como inferencias; el repositorio no puede demostrar causalidad comercial.

1. El modelo mental de Remotion

1.1 El código registra composiciones, no ejecuta un guion imperativo

`registerRoot()` registra un único componente raíz. Su implementación guarda un singleton, rechaza un segundo registro y permite que otras partes esperen hasta que el root esté disponible. La separación existe además para convivir con la reevaluación provocada por Fast Refresh ([documentación][docs-register-root], [implementación][src-register-root]).

El root declara una o más `Composition`. Cada composición combina una identidad estable, un componente o lazy component, metadata temporal/visual, defaults, schema y una función opcional para calcular metadata. El sistema de tipos permite omitir metadata estática sólo cuando `calculateMetadata` puede resolverla, y el registro guarda el contrato completo para que las demás superficies lo descubran ([Composition tipos][src-composition-types], [registro][src-composition-register]).

`Folder` agrega jerarquía de navegación sin modificar el comportamiento de la composición, y `Still` es una especialización de un solo frame ([Folder][docs-composition-folder], [Still][src-still]).

**Decisión para Resona:** copiar el root único, IDs estables, descubrimiento y folders; adaptar `Composition` a metadata musical; no inventar todavía un equivalente de `Still` si no representa una necesidad musical real.

Una composición musical candidata debería registrar, al menos:

- componente o fábrica declarativa; - ID y nombre; - defaults y schema de inputs; - BPM o tempo map, métrica y duración nominal; - sample rate, canales y política de cola; - metadata calculable para assets, duración, salidas y stems.

1.2 Una API cómoda puede compilar a primitivas más pequeñas

`Sequence` crea tiempo local: desplaza el frame observado por sus descendientes, acumula offsets al anidarse, limita duración y admite trim. Internamente calcula el origen absoluto, propaga contexto temporal y sólo monta el contenido que cae dentro del rango ([documentación][docs-sequence], [implementación][src-sequence-range], [useCurrentFrame][src-current-frame]).

`Series` no crea otro motor temporal. Aplana sus hijos, calcula recursivamente el inicio de cada segmento y los expresa como `Sequence`; offsets positivos abren huecos y negativos crean solapamientos ([Series código][src-series], [Series docs][docs-series]).

Éste es un patrón muy fuerte para Resona: ofrecer azúcar musical distinta —arreglo, patrón, clip, región, repetición— que se normalice a un único IR temporal. La API pública puede hablar de barras, beats y ticks, mientras el plan ejecutable usa posiciones de muestra enteras.

No hay que copiar la regla “fuera de rango = desmontar”. Un note release, una reverb o un delay siguen produciendo señal después de que termina el evento que los inició. En Resona, una región debe separar duración nominal, preroll, estado y cola audible.

1.3 El runtime se auto-describe para alimentar herramientas

En Studio, `Sequence` registra tracks de audio, video, imagen o secuencia con tiempo, source, efectos y referencias al origen. Esa instrumentación sólo se activa en el entorno relevante y alimenta la timeline sin convertirla en otra fuente de verdad ([registro de tracks][src-sequence-tracks]).

El bundler inyecta wrappers sobre `createElement` y los runtimes JSX para asociar componentes editables con archivo, línea y columna; el core mantiene ese stack para que Studio pueda vincular un nodo vivo con su definición ([inyección de source locations][src-source-traces], [registro de stacks][src-stack-registry]).

**Decisión para Resona:** copiar la auto-descripción del runtime y los IDs estables. La timeline, el mixer y el inspector deberían observar el modelo que produjo el programa, no inferirlo de audio ya renderizado.

2. Inputs, schemas y resolución previa

El mecanismo separado con el que Remotion enseña estos workflows a Codex, Claude Code y otros agentes está detallado en el estudio enfocado [Remotion Agent Skills](remotion-agent-skills.md).

2.1 Un pipeline de variantes explícito

Remotion resuelve una variante en etapas: defaults, `inputProps` aportados al invocar, `calculateMetadata` y configuración final. `calculateMetadata` puede ser síncrona o asíncrona, recibe un `AbortSignal`, conoce el ID y el modo de render, y puede devolver tanto props finales como metadata final ([flujo documentado][docs-props-flow], [invocación][src-resolve-config-calculate]).

La implementación conserva además la procedencia de metadata y aplica una precedencia explícita antes de validar la configuración final ([resolución y precedencia][src-resolve-config-precedence]).

Los props que cruzan la frontera se serializan con reglas explícitas. Remotion soporta JSON y marca casos especiales como `Date` y archivos estáticos; en Studio hace un round-trip temprano para detectar antes del render valores que no podrían viajar ([serialización][src-input-serialization]).

**Decisión para Resona:** copiar el pipeline, pero devolver un único `ResolvedComposition`/`RenderJob` inmutable. Así Studio, Player y renderer reciben exactamente la misma variante resuelta y no repiten inputs al seleccionar y renderizar. La propia API de Remotion exige pasar los mismos `inputProps` a selección y `renderMedia()`, una fricción que conviene evitar ([renderMedia inputs][docs-render-media-inputs]).

La fase previa de Resona debería resolver fuera del callback de audio:

- inputs y seed; - tempo map y duración; - assets y sus metadatos; - grafo, canales y buses; - instrumentos y plugins disponibles; - sample rate, formato, stems y política de tails.

2.2 Un schema que sirve al programa y a la UI

Remotion usa Zod para validar props, inferir tipos y generar controles en Studio ([schemas][docs-schemas]). La edición más nueva de elementos de timeline tiene además un `InteractivitySchema` específico, separado del schema general de props ([InteractivitySchema][docs-interactivity-schema]).

El código revela un costo que la documentación pública no hace tan visible. El core une tipos estructurales de Zod 3 y 4 e infiere props desde campos internos, aunque evita una dependencia runtime mediante imports de tipos ([AnyZodObject][src-any-zod-object], [inferencia][src-infer-zod-props]). Studio mantiene después un adaptador que interpreta `_def` y `_zod.def` para normalizar ambas versiones y elegir editores ([adaptador de Studio][src-studio-zod-adapter]). El seam está localizado, pero la interfaz pública continúa siendo específica de Zod.

**Decisión para Resona:** adaptar este patrón y definir conscientemente tres conceptos, aun si inicialmente comparten implementación:

1. validación del dominio; 2. metadata para construir controles; 3. capacidad de automatización, modulación o keyframes.

Un parámetro puede ser válido pero no editable visualmente, o editable pero no automatizable. Separar esas capacidades evita que el primer schema se convierta accidentalmente en tres APIs incompatibles.

Resona conservará esta ventaja mediante un `InputSchema<T>` propio y una `InputSchemaIR` serializable. Zod 4 será el primer adaptador oficial, no una dependencia conceptual del core ni algo que Studio deba inspeccionar directamente.

2.3 Determinismo y asincronía son parte del contrato

Remotion provee un PRNG determinista por seed y un rule de ESLint que denuncia `Math.random()`. También dispone de `delayRender()`/`continueRender()` con timeout, retry y estado explícito para bloquear el render hasta que un recurso esté listo ([random][src-random], [regla de lint][src-random-lint], [delayRender][src-delay-render]).

**Decisión para Resona:** copiar seeds explícitas y reglas estáticas; adaptar las barreras asíncronas a una fase `prepare()`. Ninguna red, I/O, promesa o evaluación de componentes debe ocurrir dentro del callback de audio en tiempo real.

3. Un contrato semántico, varias implementaciones

3.1 Preview y render no son la misma mecánica

Remotion mantiene una API de audio común, pero elige implementaciones distintas según esté previsualizando o renderizando. En preview coordina elementos de media, AudioContext, buffering, trims, loop y el estado del Player; en render registra un asset determinista con source, frame, volumen, playback rate y posición de media ([audio común][src-modern-audio], [preview][src-modern-audio-preview], [render][src-audio-rendering]).

El renderer recoge esos assets cuadro por cuadro, agrupa intervalos según presencia e ID, construye curvas de volumen, prepara pistas y las mezcla/comprime después ([reconstrucción][src-asset-positions], [mezcla][src-create-audio]).

Esto enseña dos cosas distintas:

- **copiar:** un componente semántico puede tener adapters de preview y render; - **no copiar:** la mecánica de assets por frame no sirve como motor musical.

Resona necesita que ambos adapters ejecuten el mismo plan musical y el mismo contrato DSP. El backend de tiempo real puede usar AudioWorklet, WASM o un proceso nativo, y el offline puede avanzar más rápido que el reloj; la equivalencia auditiva y numérica debe definirse y probarse.

3.2 React debe quedar fuera del núcleo puro

El paquete `remotion` publica una entrada `remotion/no-react`, y renderer, bundler y CLI la usan para tipos, validaciones y utilidades sin cargar la superficie React ([export `no-react`][pkg-core-no-react], [uso en renderer][src-asset-positions]).

**Decisión para Resona:** copiar y profundizar ese límite. Timing, IR, validación, scheduler y DSP no deben depender de React. React puede ser una frontend declarativa que produce el IR; el engine debe poder ejecutarlo desde Node, tests, Studio u otro lenguaje anfitrión.

4. Bundling y evaluación

4.1 El bundle es un artefacto reutilizable

`bundle()` resuelve el entry point, exige que registre un root, compila la entrada del usuario junto con entradas generadas para Studio, maneja assets públicos y produce una carpeta o URL servida. La documentación recomienda compilar una vez y reutilizar el resultado para varios renders, en vez de bundlear cada variante ([bundle docs][docs-bundle], [bundle pipeline][src-bundle-pipeline], [validación y retry][src-bundle-validation]).

La configuración común fija aliases para evitar múltiples React/Remotion, loaders de assets y CSS, source maps, cache persistente y un hash de configuración. Rspack y webpack quedan detrás de una seam común con overrides ([config compartida][src-bundler-shared], [Rspack][src-rspack]).

Studio agrega entradas generadas en orden —refresh, entorno, source traces, código del usuario, shim y UI— y el HTML resultante incluye versión tanto de Remotion como del contrato del sitio ([entry points][src-studio-entry-points], [HTML y versión][src-studio-html]).

**Decisión para Resona:** adaptar el pipeline a:


entry TS/TSX + assets
        ↓
bundle evaluable
        ↓
registro + resolución de variante
        ↓
ProjectIR normalizado y versionado

El bundle es el artefacto de código; el IR es el contrato musical; el plan DSP es el artefacto ejecutable. No conviene confundirlos ni soportar dos bundlers en el MVP.

5. Renderer y la divergencia esencial del audio

5.1 Lo que sí hay que copiar del orquestador

La API de alto nivel separa `selectComposition()` de `renderMedia()`. El selector carga el bundle, espera que esté listo, ejecuta la resolución de metadata una vez y devuelve una configuración serializada. `renderMedia()` valida temprano, calcula concurrencia y memoria, reporta progreso por fases, admite cancelación y hace cleanup explícito ([selectComposition][src-select-composition], [renderMedia setup][src-render-media-setup], [renderMedia cleanup][src-render-media-cleanup]).

**Decisión para Resona:** copiar la orquestación y sus responsabilidades:


compile/evaluate
    → resolve composition
    → validate plan
    → create clean engine
    → process offline blocks
    → encode mix/stems
    → cleanup

Progreso, cancelación, ownership de recursos y cleanup no deberían agregarse después; son parte del contrato inicial del renderer.

5.2 Lo que no hay que copiar

Remotion distribuye cuadros entre una pool concurrente, reintenta cuadros por página y luego entrega el resultado en orden al encoder. Esa estrategia es correcta cuando cada frame visual puede evaluarse por su posición ([pool de frames][src-render-frames], [pipe ordenado][src-render-media-pipe]).

Un sintetizador, delay, reverb, compresor o automatización depende de lo procesado antes. Resona no debe paralelizar muestras o bloques temporales arbitrarios. Sólo podrá paralelizar pistas o regiones cuando defina de forma comprobable estado inicial, warm-up, latencia, interacción, tails y merge.

Tampoco debe usar Chromium para producir audio ni reconstruir la timeline mirando qué assets aparecieron en cada frame. El modelo musical debe declarar de antemano eventos, rutas, automatizaciones y procesadores; el motor debe avanzar ese plan de forma continua.

5.3 Un backend nativo es una seam posible, no una decisión inicial

Remotion distribuye compositor nativo por plataforma y lo opera como proceso persistente con mensajes tipados, nonce y streaming ([resolución del binario][src-native-resolver], [protocolo del proceso][src-compositor]).

Esto es una referencia útil si Resona termina aislando un engine Rust/C++/WASM detrás de Node, pero decidirlo antes de probar el scheduler, el grafo y la paridad preview/offline sería prematuro.

6. Player: una superficie embebible, no una miniatura de Studio

El Player acepta directamente componente, duración, FPS, dimensiones e input props; no exige que el consumidor monte una `Composition`. Internamente crea el contexto necesario para reutilizar el core ([API del Player][docs-player-api], [contexto sintético][src-player-context]).

Su ref expone play, pause, seek, volumen, fullscreen y eventos. El playback coordina gesto de usuario, AudioContext, elementos precalentados, buffering, loop y un reloj basado en `requestAnimationFrame`/timeouts apropiado para el timeline visual ([métodos][src-player-methods], [play/pause][src-player-use-methods], [reloj][src-player-playback]).

**Decisión para Resona:** copiar un `@resona/player` pequeño, embebible, controlable por ref y eventos. Adaptar el transporte: el reloj autoritativo debe ser el engine de audio; React, la playhead y las visualizaciones siguen ese reloj, nunca lo gobiernan.

Conviene modelar `buffering`, `preparing`, `playing`, `paused`, `seeking`, `ended` y `error` como estados observables. Remotion ya separa buffering de play/pause y permite preparar recursos antes de que entren en escena ([buffer state][docs-buffer-state], [premount][docs-premount]).

7. CLI y opciones compartidas

7.1 La CLI es un adapter, no otro engine

El entry de CLI enruta comandos, valida compatibilidad de versiones antes de ejecutar y centraliza errores y cleanup. El comando `render` reúne argumentos y configuración pero termina en el mismo flujo que usa bundler, selector y renderer programático ([router][src-cli-index], [render adapter][src-cli-render], [flujo compartido][src-cli-render-flow]).

**Decisión para Resona:** comenzar con tres comandos:


resona studio <entry>
resona compositions <entry>
resona render <entry> <composition-id> <output>

La API programática debe existir primero; la CLI sólo resuelve archivos/flags, muestra progreso y traduce errores a exit codes.

7.2 Una opción se define una sola vez

Remotion modela cada opción con nombre, flag de CLI, nombre de API SSR, descripción, docs, tipo, setter de config y una función que devuelve tanto valor como procedencia. Un mapa central reutiliza esos descriptores para construir tipos y superficies; opciones como concurrencia o codec codifican precedencia y validan conflictos ([descriptor][src-option], [mapa][src-options-map], [concurrencia][src-concurrency-option], [codec y precedencia][src-codec-option]).

**Decisión para Resona:** copiar este patrón desde el primer flag. Sample rate, formato, bit depth, canales, stems, tail, normalización, seed y concurrencia deben tener una definición canónica reutilizada por config, CLI, API y Studio, con `source` visible para diagnóstico.

7.3 El skew de versiones se trata como error de producto

La CLI explica paquetes desalineados y el core detecta múltiples versiones cargadas; una prueba de monorepo exige que dependencias internas compartan versión ([doctor de versiones][src-cli-versions], [warning runtime][src-multiple-versions], [invariante][test-same-version]).

**Decisión para Resona:** si publicamos varios paquetes coordinados, validar versiones en CLI y runtime desde el principio. El error debe señalar paquete encontrado, versión esperada y acción correctiva.

8. Studio: frontend, backend y protocolo explícito

8.1 El servidor de desarrollo es una pieza propia

El preview server combina bundling, file watching, HMR/SSE, rutas de API y lifecycle del puerto. Un mapa exhaustivo asocia cada path con tipos request/response y el backend debe implementar un handler por ruta ([preview server][src-preview-server], [contratos][src-api-contracts], [dispatch][src-api-routes]).

Los eventos server-to-client son una tagged union; el servidor mantiene clientes SSE y puede hacer broadcast o unicast. Entre los eventos hay cambios de bundle, progreso, errores, actualizaciones de timeline y operaciones de edición ([eventos][src-live-event-types], [servidor SSE][src-live-events]).

**Decisión para Resona:** copiar la separación:


@resona/studio          frontend
@resona/studio-server   filesystem, build, engine y render jobs
@resona/studio-shared   contratos de API y eventos

SSE basta para HMR, progreso y eventos de baja frecuencia. Meters, waveform streaming o datos de transporte de alta frecuencia pueden necesitar WebSocket, SharedArrayBuffer u otro canal; no deberían inflar el protocolo de control.

8.2 Seguridad local sigue siendo seguridad

Las mutaciones del servidor validan same-origin, y el protocolo para integraciones externas versiona capabilities, limita la vigencia de targets y pide confirmación antes de instalar contenido ([same-origin][src-same-origin], [discovery][src-studio-discovery], [instalación][src-install-in-studio]).

**Decisión para Resona:** copiar validación de origen, rutas con targets dentro del proyecto, payloads acotados y confirmaciones explícitas. Un Studio local que puede escribir código, descargar assets o cargar plugins tiene una superficie de seguridad real.

9. Edición visual que persiste al código

9.1 Remotion no pretende editar JavaScript arbitrario

Studio permite cambiar ciertos props, tener undo/redo y guardar al archivo fuente, pero sólo reconoce formas estáticas. Expresiones complejas quedan read-only; las guías piden valores inline, literales y patrones de interpolación reconocibles ([interactividad][docs-interactivity], [restricciones][docs-interactivity-best-practices]).

El round-trip no es un `replace()` textual:

- el bundler conecta nodos vivos con ubicaciones de código ([source traces][src-source-traces]); - el servidor parsea y transforma AST, y rechaza una `Composition` cuyo objeto no sea hardcoded ([codemod defaults][src-update-default-props]); - una cola serializa escrituras y la ruta valida que el archivo esté dentro del proyecto, aplica el cambio, formatea y coordina watchers/HMR ([write queue][src-write-queue], [ruta][src-update-default-props-route]); - cambios multiarchivo se agrupan como transacción y el undo guarda snapshots ([save sequences][src-save-sequences], [undo][src-undo-stack]); - si el usuario modifica externamente un archivo implicado, el historial relevante se invalida para no pisarlo ([cambios externos][src-undo-external]).

9.2 Qué significa esto para Resona

La promesa “la UI edita el código” es valiosa y coherente con el ADR de fuente versionable, pero es un editor estructural, no un formulario. Requiere un subconjunto de autoría bien definido, identidad estable, parser, formatter, diffs, escritura atómica, undo transaccional y resolución de cambios externos.

**Decisión:** adaptar después del primer corte vertical. Dos caminos viables son:

1. AST sobre un subconjunto TS/TSX deliberadamente editable, dejando el resto read-only; 2. un manifest declarativo serializable importado por código, más fácil de editar sin crear una segunda fuente canónica.

No conviene ocultar estado musical en una base de datos de Studio ni prometer que cualquier expresión TypeScript será editable. El primer Studio debería observar, reproducir y depurar; el writeback llega cuando el IR y el lenguaje de autoría sean estables.

10. Tests y contratos de calidad

Remotion separa suites de unidad, render real, SSR/bundle, templates, browser Studio y otros subsistemas. Turbo expresa dependencias de build y un gate agregado, mientras `it-tests` divide render, SSR, bundle, WebCodecs y contratos del monorepo ([scripts raíz][pkg-root-scripts], [Turbo][turbo-tasks], [it-tests][pkg-it-tests]).

Las pruebas no se quedan en snapshots de funciones. Hay integraciones que generan media real y la inspeccionan con herramientas externas; por ejemplo, el test de sample rate renderiza, ejecuta `ffprobe` y comprueba 44.1 kHz y el default de 48 kHz ([sample rate real][test-sample-rate]). También hay pruebas de exactitud de cuadros con codecs distintos, del protocolo HTTP de Studio, golden tests de codemods, export maps y uniformidad de versiones ([frame accuracy][test-frame-accuracy], [protocolo][test-studio-protocol], [codemod][test-update-default-props], [exports][test-exports], [versiones][test-same-version]).

**Decisión para Resona:** copiar la pirámide, cambiando sus oráculos por audio:

- unit: conversión bar/beat/tick -> sample, orden MIDI, curvas, validación de grafo; - engine: voces, note-off, automatización, latencia, reset y tails; - renderer real: WAV/FLAC válido, sample rate, canales, sample count y stems; - determinismo: PCM idéntico bajo el backend acordado o tolerancia numérica explícita; - paridad: preview y offline sobre el mismo fixture; - transporte: seek, loop, preroll y snapshots con un delay stateful; - protocolo/writeback: payloads, seguridad, golden diffs, undo y cambios externos; - paquete: exports, dependencias permitidas y versiones coordinadas.

11. Monorepo y límites de paquetes

Los límites maduros de Remotion siguen runtimes y despliegues: core React/browser, Player embebible, bundler Node, renderer Node/native, Studio frontend, Studio server y contratos compartidos. Los manifests muestran dependencias dirigidas —por ejemplo Player depende del core, CLI compone bundler/renderer/Studio y renderer distribuye binarios opcionales por plataforma— ([core][pkg-core], [Player][pkg-player], [CLI][pkg-cli], [renderer][pkg-renderer], [Studio shared][pkg-studio-shared]).

El monorepo raíz usa Bun workspaces y Turbo y ya tiene muchas suites y paquetes especializados ([workspace][pkg-root-workspaces], [Turbo][turbo-tasks]). Esa escala es evidencia del producto actual, no una plantilla para el día uno.

**Decisión para Resona:** copiar seams, no cantidad. Una forma inicial razonable es:


resona                 DSL pública, tipos y registro
@resona/engine         IR, scheduler, grafo y contrato DSP sin React
@resona/renderer       ejecución offline y encoders
@resona/player         transporte embebible
@resona/studio         UI de desarrollo
@resona/cli            adapter de comandos

`studio-server` y `studio-shared` pueden empezar como límites internos y separarse cuando exista consumo independiente. `bundler` tampoco necesita ser paquete público hasta tener más de un consumidor estable.

No copiaría la exportación amplia de internals ni abriría muchas extensiones antes de tener un vertical slice. La API pública debe ser pequeña y el IR puede versionarse sin publicarlo como un conjunto de estructuras mutables.

12. Patrones de producto e ingeniería que plausiblemente explican su éxito

> Esta sección es una inferencia razonada a partir del producto y del snapshot, no una prueba > causal. No usa métricas históricas, contributors ni popularidad del repositorio.

12.1 Una frase comprensible y una demostración inmediata

El README expresa que React es la fuente de verdad y presenta programación, edición y agents como workflows intercambiables sobre el mismo proyecto. El onboarding empieza con un solo comando y enlaza templates ([mensaje][readme-source-of-truth], [onboarding][readme-onboarding]).

**Inferencia:** “hacer videos programáticamente” es una categoría fácil de repetir, y el primer resultado visible requiere poca ceremonia. Resona necesita una frase igual de clara y un ejemplo audible en minutos: “componé, reproducí y renderizá música programable desde la misma fuente”.

12.2 Un camino continuo desde juguete hasta producción

El mismo componente puede verse en Studio, embeberse con Player y renderizarse desde Node; el bundle puede reutilizarse para múltiples variantes ([Player integration][docs-player-integration], [SSR][docs-ssr], [bundle][docs-bundle]).

**Inferencia:** la continuidad reduce el salto entre experimento y producto. El equivalente de Resona debe ser una composición que suena en Studio, se integra en una app y se renderiza en batch sin ser reescrita.

12.3 Documentación y errores son parte del producto

El monorepo compila ejemplos con Twoslash, el CLI enlaza documentación en su ayuda y el runtime incluye errores accionables y diagnóstico de versiones ([docs build][pkg-docs], [ayuda CLI][src-cli-help], [version doctor][src-cli-versions]).

**Inferencia:** una API novedosa necesita feedback pedagógico. Resona debería documentar cada primitiva con ejemplos ejecutables y hacer que errores de timing, assets, plugins o grafo apunten a una solución concreta.

12.4 Un núcleo pequeño rodeado por superficies especializadas

El registro y la composición son conceptos relativamente pequeños; Player, renderer, Studio, server y CLI viven en paquetes con responsabilidades distintas ([registerRoot][src-register-root], [manifests][pkg-player]). El repositorio incluye además un scaffolder y múltiples paquetes/templates especializados ([create-video][pkg-create-video], [README ecosystem][readme-ecosystem]).

**Inferencia:** el núcleo fácil de aprender habilita un ecosistema sin obligar a todos a cargar todas las superficies. Resona debe lograr primero un core musical pequeño y extensible; la amplitud de instrumentos, efectos, cloud y templates puede crecer después.

12.5 Restricciones explícitas en vez de magia frágil

La edición visual documenta qué formas de código puede modificar y deja el resto read-only; el renderer valida opciones antes de hacer trabajo costoso ([restricciones][docs-interactivity-best-practices], [validación][src-render-media-setup]).

**Inferencia:** límites honestos aumentan la confianza. Para Resona es mejor declarar qué parte de una composición puede editar Studio y qué contrato de paridad ofrece el engine que simular compatibilidad universal.

14. Arquitectura objetivo derivada

La síntesis recomendada es:


┌──────────────────────────────────────────────────────────────┐
│ Fuente del autor: TS/TSX + datos + assets                    │
└──────────────────────────────┬───────────────────────────────┘
                               ↓
                    bundle y evaluación aislada
                               ↓
            defaults + inputs + calculateMetadata/prepare
                               ↓
┌──────────────────────────────────────────────────────────────┐
│ ProjectIR versionado                                         │
│ tempo · tracks · clips · MIDI · graph · FX · automation     │
└──────────────────────────────┬───────────────────────────────┘
                               ↓
                    validación y compilación
                               ↓
┌──────────────────────────────────────────────────────────────┐
│ ExecutionPlan inmutable                                      │
│ eventos ordenados · samples · buffers · latencias · tails   │
└──────────────────────┬───────────────────────┬───────────────┘
                       ↓                       ↓
              realtime engine          offline renderer
                       ↓                       ↓
                Studio / Player           mix / stems

Propiedades importantes de esta frontera:

- La capa declarativa no procesa muestras. - El IR no depende de React ni de Studio. - Toda posición musical se normaliza una vez a samples con una regla de redondeo explícita. - El engine comienza cada ejecución desde estado limpio. - Seek y loop usan preroll o snapshots definidos, no un salto de playhead cosmético. - Duración nominal y tail audible son conceptos diferentes. - Preview y offline consumen el mismo `ExecutionPlan`; cualquier diferencia de backend se declara y se prueba. - Studio observa el IR y el estado del engine; no crea un modelo musical paralelo.

15. Primer corte vertical recomendado

El primer hito debería probar una única historia end-to-end y evitar una DAW UI completa:

1. Registrar una composición con ID, defaults, schema, BPM, duración y sample rate. 2. Declarar un `AudioClip`, un clip de eventos que alimente un instrumento simple y un delay. 3. Normalizar todo a un IR inspeccionable. 4. Reproducirlo en una página Studio con play, pause, seek y loop. 5. Renderizar el mismo plan a WAV desde una API y una CLI fina. 6. Cambiar un input y producir una variante sin duplicar la composición. 7. Repetir el render desde estado limpio y verificar el contrato de determinismo.

Gates de aceptación

- El WAV tiene sample rate, canales, duración y sample count esperados. - Eventos MIDI simultáneos conservan un orden definido. - El delay prueba estado, reset, preroll de seek y política de tail. - Preview y offline coinciden dentro de una tolerancia documentada. - Dos renders con la misma seed cumplen el contrato de igualdad elegido. - Cancelar cierra engine, archivos temporales y encoder. - Un error muestra composición, nodo/track y ubicación de fuente cuando exista. - CLI y API resuelven las opciones con la misma precedencia y reportan su procedencia.

Deliberadamente fuera de este corte

- edición de piano roll o timeline que escriba al código; - mixer completo, feedback, sidechain y compensación general de latencia; - VST/AU y sandbox de plugins de terceros; - colaboración, cloud rendering y marketplace; - engine nativo multiplataforma antes de medir la implementación mínima; - muchos packages públicos y compatibilidad con varias frontends de autoría.

16. Decisiones que el prototipo debe contestar

1. ¿React/TSX resulta una capa de autoría natural para música o conviene una DSL de datos con wrappers React opcionales? 2. ¿Cuál es la representación canónica de posiciones y qué redondeo usa al pasar a samples? 3. ¿Qué igualdad se promete entre preview y offline: perceptual, sample-exact por plataforma o bit-exact cross-platform? 4. ¿Cómo se representa el estado serializable de un instrumento/efecto para seek, loop y render distribuido? 5. ¿La cola se corta, se calcula, se declara o combina políticas? 6. ¿El primer engine vive en AudioWorklet/WASM, en Node o detrás de un proceso nativo? 7. ¿Qué subset podrá editar Studio sin romper abstracciones del autor? 8. ¿El manifest serializable es una ayuda de round-trip o introduce una segunda verdad?

La secuencia prudente es responder primero tiempo, IR, engine y paridad; después diseñar la edición visual. Ésas son las decisiones irreversibles. La timeline bonita es una consumidora de esas respuestas, no su sustituto.
